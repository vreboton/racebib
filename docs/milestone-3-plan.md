## Implementation sequence

1. **Set the API and lifecycle rules.** Stay with ASP.NET Core controllers, EF Core/MySQL, Vue/Vuetify and the existing HTTP client. Use event-scoped course and race routes under `/api/v1/events/{eventId}` and scope checkpoints, categories and waves through their parents. Resolve the organizer from the stored event, match every child against the full parent path and check the shared authorization service before mutations. Use DTOs and existing `ProblemDetails` conventions for invalid input and conflicts. Allow configuration writes through RegistrationClosed, and lock writes at Ready, Live, Completed and Cancelled. Keep current event transitions and legacy event behavior compatible. For configured events, validate the active configuration when moving to Ready. Guard event date changes that would strand a race or wave outside the event window.
2. **Build the course and checkpoint workflow first.** Race creation requires a course. Let directors create a course and edit its ordered checkpoints in Event Details before creating a race. Reuse event/name/version as the initial version family and keep its name stable once versioned. Clone metadata and checkpoints transactionally to a new version, preserving existing race references. Treat versions assigned to races as immutable. Require explicit reassignment of an eligible race to a new version and reject changes to races with registrations. Handle concurrent version allocation through the existing unique constraint and a conflict response. Validate trimmed names and codes, positive course distance within stored precision, unique codes and contiguous positive sequence numbers, nondecreasing checkpoint distances within the course distance, one start and one finish for a usable course, and consistent cutoff fields. Save ordering atomically and handle MySQL unique-index collisions during swaps. Preserve checkpoint IDs on edits within an editable version.
3. **Deliver race CRUD in the same event screen.** List and open races, create against an eligible same-event course revision, and edit the name, description, start and cutoff. Default distance from the chosen course and enforce consistency at the API boundary. Require a positive cutoff when supplied and a start inside the event window. Deactivate races with operational history and preserve related records. Allow hard deletion only for unused configuration after checking dependents, or ship deactivation as the delete operation for the first release. Require explicit confirmation in the UI and use transactional guards where state can change concurrently.
4. **Add race categories and start waves.** Validate trimmed category names, uniqueness within a race, nullable nonnegative inclusive age bounds and minimum ≤ maximum. Keep overlapping categories valid unless eligibility rules explicitly require exclusivity. For waves, require a positive unique sequence and positive capacity when set. Keep active wave times in sequence order, at or after race start and within the event window. Prevent parent edits from invalidating existing wave schedules. Use an offset-aware API timestamp, store UTC and render the event time zone in the UI. Disallow nonexistent local times and let the director disambiguate repeated times. Preserve registration references when categories or waves are deactivated. Keep runner assignment and wave capacity enforcement during registration outside this milestone.
5. **Finish the race-director workflow.** From Event Details, give the director a clear path to configure a course, review the ordered checkpoints, create a race, add categories and schedule waves. Use existing components for loading, empty and error states. Explain locked controls and show field errors where the director can correct them. Confirm course revision switches and deactivation. Refresh persisted state after mutations and surface conflict responses so a stale form can reload safely.
6. **Verify locally.** Extend existing backend authorization tests, MySQL `WebApplicationFactory` tests and frontend Vitest patterns. Exercise live HTTP and browser workflow against `docker compose up --build` using a disposable local MySQL 8.4 database. Use `RACEBIB_MYSQL_TEST_CONNECTION` with the existing dedicated test-database guard and set `RACEBIB_MYSQL_TEST_REQUIRED` for the integration pass. Check fresh initialization and upgrade from the pinned base if a migration is needed. Build the frontend, run `dotnet test` for the API test project and run the frontend package tests. Reuse the existing Compose stack and dependencies.

## Risks and acceptance criteria

- **History and deletion.** Existing foreign keys include cascading delete paths. A race with registrations retains its course revision, category and wave references through all supported lifecycle operations. Retired rows remain readable where needed for history. Cloning a course leaves previous checkpoints and race references intact.
- **Scope and lifecycle.** A RaceDirector and EventAdministrator can configure their own eligible event end to end. Unauthenticated requests, other organizers, inactive memberships and suspended organizations receive the appropriate denial. Mismatched parent-child IDs fail, including between events of the same organizer. Ready and later locked states reject configuration changes through direct API calls. Existing event lifecycle flows continue to work for legacy events.
- **Concurrent and invalid edits.** MySQL tests cover competing version allocation, order swaps and rollback after an invalid reorder. Duplicate names/codes, invalid distances, flags, ages, capacities and dates produce actionable errors. Failed updates leave the prior configuration intact. Verify storage precision and case-insensitive uniqueness against MySQL.
- **Scheduling.** A director can enter a local race or wave time in the event zone, reload the race and see the same scheduled time. Cover overnight events, daylight-saving boundaries, invalid wave ordering and event/race date edits that would invalidate child schedules.
- **Local delivery.** The Docker Compose workflow starts and serves the existing app, an authorized director completes configuration from Event Details, and the result survives refresh and a restart using the same local volume. Automated tests exercise both successful and denied paths. This report is a static audit. No implementation, Compose run, or runtime verification was performed.
